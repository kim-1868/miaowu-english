# S14：已登录读者修改密码与账号恢复边界

更新：2026-11-01。**开发分支安全功能，未部署到用户已验收的 Pages 测试站；不能视为已上线的忘记密码服务。**

## 已实现：读者主动修改密码

在「我的书房」显示「修改登录密码」，用户输入：原密码、新密码、确认新密码。

- POST `/api/auth/change-password` 必须已经登录，携带同源 Origin 与有效 Session。
- 后端查询当前账号哈希，实际验证**原密码**；新密码需满足现有 `validPassword`（10–128 字符、UTF-8 最高256字节），且与原密码不同；服务端限速防止穷举。
- SQL 使用原哈希+盐作为条件更新，依靠 D1 原子批处理撤销全部旧会话，随后仅给当前设备签发新的 Secure / HttpOnly / SameSite=Lax 登录 Cookie。
- 修改后别的设备必须重新登录；用户的分类阅读权益、书籍进度、记忆藏书票、剧情回声数据均不删除。
- 并发改密发生冲突时拒绝、要求重试，不能在一个请求里部分修改密码/会话。
- 新旧密码不得出现在日志、URL 或 D1 明文字段中。仅存服务器端经 PBKDF2+Pepper 的加盐密码哈希。原有密码存储设计在正式商用前仍需独立安全审查。

## 这还不是“忘记密码”功能

仅知用户名或购买的分类兑换码，**不足以证明账号所有权**：兑换码可能被复制、订单也可能转让/他人知晓，因此绝不可提供不需要身份核验的公开重置端点。

正式上线前二选一并完成安全审计：

1. **推荐的自助找回**：注册时验证邮箱归属，绑定 verified-email 到 user id；通过一次性、短期、强随机、不可重放的重置链接完成找回，所有现有 session 作废；需接入可靠的邮件服务商、配置发信域名与发送速率限制；邮件地址属于个人信息，必须纳入隐私政策与删除机制。
2. **低成本人工找回**：经过多因素订单证据、收款平台交易核验、人工审核及完整操作审计后，由有权限的运营人员发起有过期时间的一次性找回流程；不泄漏原密码，也不得仅凭“提供订单号或兑换码”直接改密码。人工找回后台目前不存在，不可对外承诺已开通。

如果暂时没有可信的找回渠道，不能将“永久可找回”写入付费商品说明。上线前明确用户支持政策，不能用泄露敏感账号记录的方式救急。

## 人工 QA（部署到独立测试环境之后）

1. 用户 A 已有 CET4 权益，并在两台设备登录 A。
2. A 用原密码成功修改；当前设备继续打开《四级》受限章节、`/api/auth/me` 与个人词卡；另一个设备会话被服务器拒绝。
3. 用旧密码登录应失败，新密码登录成功；原账号 D1 的 CET4 类别授权、读章进度与复习记录仍存在。
4. 错误原密码、新密码过短、重用原密码与跨站 Origin 必须被拒绝；不注销原会话，也不得改变原密码。
5. 不登录直接访问改密接口必须返回 401；前端不能把密码放在网页地址或错误弹窗中。
6. 客户端表单必须显示一致的中文反馈，验证手机浏览器深浅色模式和点击键盘提交体验。

本地自动测试使用假账号 + 内存 SQLite + 实际 Worker fetch；不写任何线上 D1，不产生真实密码/账号数据。
